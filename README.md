# R&D 신규사업 예산 심의 시뮬레이터 (RDAgents)

국가 R&D 신규사업 예산 심의 과정을 LangGraph 기반 멀티 에이전트 환경에서 시뮬레이션하는 시스템입니다.
실제 심의 전에 기획보고서의 취약점을 찾아 보완하고, 심의위원의 예상 질의에 미리 대비하는 것이 목적입니다.

## 아키텍처

- **분석가 9명**: 분야 기술전문가 3명 + 기능별 분석가 6명(기술 가치, 기술 트렌드/중복성, 경제/재무 타당성, 정책 부합성, 수행체계, 규제/윤리)
  - 기술전문가는 사업 유형에 따라 구성 (`agents/utils/committee.py`). 공공임무형·혼합형: 재난 위험·현상, 재난안전 ICT·데이터, 방재·현장 대응 실무. 산업형: 핵심 원천기술, 응용·시스템 통합, 실증·사업화
  - Groq 하루 한도 때문에 기술전문가 3명은 노드 하나에서 전문가별 절로 씀
- **쟁점 원장** (`dataflows/issue_ledger.py`): 쟁점 등록 노드가 분석 보고서의 지적을 쟁점으로 옮기고, 코드가 사전 점검 누락·숫자 검산 불일치를 앞에 더함. LLM이 단 출처는 코드가 원문 줄·인용 구절과 대조 → `02b_쟁점원장.md`
- **쟁점별 심사 공방**: 쟁점을 하나씩 상정(예산·사전 점검 누락·3대 기준 '상' 쟁점은 반드시, 그다음 출처 검증된 쟁점을 심각도 순)
  - **질의 위원은 쟁점의 기준에 따라 코드가 배정**: 공공임무형은 기술위원·재난안전 정책위원·**현장 실무위원**·재정위원·법·제도위원
  - **발표자는 제출자료 근거로만 답함** (구조화 출력: 근거 있음/없음·답변·출처·인용 구절). 출처·인용이 원문과 다르거나 원문에 없는 수치로 방어하면 코드가 방어 실패로 판정
  - 공방 길이는 쟁점 수 상한(`max_debate_issues`, 기본 6, test-groq 4)으로 정함
- **전문위원회 위원장**: 쟁점 원장과 공방을 종합해 1차 의견. 결론과 다른 의견은 **소수의견**으로 기록
- **기획처 내부 검토 (3자 토론)**: 예산 조정관의 1차 조정안을 바탕으로 적극 투자 vs 재정 건전성 vs 균형 조율관 간의 재정 검토 토론
- **최종 승인권자**: 쟁점 원장·위원장 의견·예산안·재정 토론을 종합해 최종 결정. **판정 정합성**: 3대 기준 '상' 쟁점이 방어 실패로 남아 있으면 '승인'을 거부(조건부승인 이하), 근거 예산 없는 승인 예산도 거부. 소수의견 기록
- **예상 질의 추출기**: 쟁점 원장(방어 실패·미상정 쟁점 우선)과 심의 이력에서 예상 질의(+권장 답변 초안)와 보완 권고를 도출
- **독립 품질평가자**: 사업 유형별 기준 정량 점수·신뢰도와 불일치·반대 근거·누락 자료를 별도 감사
- **재심의 비교자**: 이전 지적의 해소·미해소·신규 우려와 결정·예산 변화를 비교

모든 에이전트는 공통 심의기준을 적용합니다 — 최우선 평가 항목은 **정부지원 필요성, 기술개발의 중요성, 시급성**이며,
기준 정의는 `rdagents/agents/utils/review_criteria.py` 한 곳에서 관리됩니다.

### 사업 유형별 심의기준 (공통 핵심 + 유형 모듈)

심의 시작 전에 코드가 원문 키워드로 사업 유형을 한 번 판별하고(`dataflows/project_type.py`, LLM 없음),
모든 노드가 같은 유형의 기준을 씁니다. 판별 결과와 근거 줄은 `00b_사전점검.md` 맨 앞과 HTML 리포트 사업 개요에 남습니다.
판별이 틀리면 `--project-type 산업형|공공임무형|혼합형`(또는 `RDAGENTS_PROJECT_TYPE`)으로 지정합니다.

| 유형 | 판별 (키워드가 나온 줄 수) | 기준 모듈의 중점 |
|---|---|---|
| 공공임무형 | 재난·피해·인명·소방·대피 등이 산업·시장 키워드의 2배 이상 | 국가 책무, 피해저감·공공가치, 재난관리 단계(예방·대비·대응·복구) 적합성, 현장 적용·확산(수요기관 참여·제도화·사후 운영 재원), 부처 간 역할 분담, 억지 B/C 대신 비용효과성 |
| 산업형 | 시장·매출·수출·사업화 등이 공공 키워드의 2배 이상 | 시장실패·민간 매칭, 기술 주권·산업 파급, 사업화·확산, 시장성 |
| 혼합형 | 그 밖 (원문이 없을 때도) | 주된 성격을 근거와 함께 밝히고 한쪽 잣대로 다른 쪽을 감점하지 않음 |

유형에 따라 바뀌는 것:
- **심의기준 문구**: 분석가 6명·패널·발표자·위원장·질의 추출기에 유형 모듈 주입
- **정량 평가표 가중치** (`TYPE_QUALITY_WEIGHTS`, 비교·점검용 초안이며 공식 배점 아님)
  - 공공임무형: 정부지원 20 · 공공가치·피해저감 20 · 시급성 15 · 재난관리 단계 적합성 10 · 현장 적용·확산 15 · 기술적 실현가능성 8 · 수행 역량·부처 간 역할 7 · 비용효과성 5
  - 산업형: 정부지원 20 · 기술 주권·산업 파급 20 · 시급성 15 · 실현가능성 15 · 경제성·시장성 15 · 사업화·확산 10 · 수행 역량 5
  - 혼합형: 정부지원 20 · 중요성·공공가치 20 · 시급성 15 · 실현가능성 15 · 경제·공공가치 10 · 현장 적용·사업화 10 · 수행 역량 10
- **사전 점검 항목**: 공공임무형·혼합형은 공통 9개에 수요기관 참여·재난관리 단계 명시·제도화·표준화 경로·운영·유지관리 재원 4개 추가
- **필수 예상 질의**: 공공임무형은 '현장 적용·확산' 질의 1건 이상 (재난안전 R&D는 개발한 기술이 현장에 쓰이지 않는다는 지적이 잦음)

## 설치 및 실행

```bash
# 가상환경 생성 (권장)
python -m venv venv
venv\Scripts\activate

# 패키지 설치
pip install -e .

# 환경 변수 설정
# .env.example을 .env로 복사하고 API 키를 입력하세요.
# 기본 프로바이더는 Groq입니다. GROQ_API_KEY를 설정하세요. (Cerebras는 정책 변경으로 지원 중단)
# 기본 모델: openai/gpt-oss-120b (Deep/Quick 공통)

# 실행 (샘플 JSON 모드)
python main.py --project quantum_computing

# 짧은 컨텍스트·저비용 검증 프로필: Groq 무료 등급 (.env에 GROQ_API_KEY). 분당 8,000토큰·하루 20만 토큰이라 심의 1회(약 11만 토큰)는 하루 한도가 넉넉할 때
# Groq gpt-oss는 구조화 출력을 json_schema 방식으로 요청합니다 (도구 호출 방식은 tool_use_failed가 잦음)
# 분당 8,000토큰에 맞춰 분석가가 보내는 도구 결과를 3,500자로 줄이고(RDAGENTS_TOOL_RESULT_CHAR_BUDGET),
# 분석가 1명의 도구 호출을 3번으로 제한합니다(RDAGENTS_MAX_ANALYST_TOOL_CALLS). 환경변수가 프로필보다 우선합니다.
# 출력 상한(3,072토큰, 추론 포함)에서 잘리지 않게 짧은 문맥 모드에서는 분석가 보고서(2,500자 이내)와
# 예상 질의(5~7개)를 짧게 쓰도록 지시합니다. 상한을 올리면 입력과 합쳐 분당 한도에 걸려 413이 납니다.
python main.py --project quantum_computing --profile test-groq

# 실행 전 토큰 추정 (API 호출 없음): 가짜 LLM으로 그래프를 한 번 돌려 노드별 요청 크기와 총 토큰을 셈
# 요청 하나가 분당 한도를 넘는지(넘으면 413), 하루 한도 안에 끝나는지 미리 확인. 한도는 RDAGENTS_TPM_LIMIT/RDAGENTS_TPD_LIMIT
# --execution-id를 주면 체크포인트에서 이어서 실행할 남은 부분만 셈
python main.py --report "기획보고서.md" --profile test-groq --estimate-tokens [--execution-id ID]

# 저장된 결과를 LLM 없이 지금 코드로 다시 렌더링 (검증보고서·원문에 없는 수치 표시·HTML). 검증 규칙을 고친 뒤 지난 결과에 적용
python main.py --rerender --run-dir "results/{사업ID}/{실행ID}" --report "기획보고서.md" [--evidence ...]

# 두 실행 결과를 같은 지표로 비교 (잘린 응답, 유효 인용, 원문에 없는 수치, 예상 질의 수·기준, 숫자 검산 반영, 토큰)
# 공정하게 비교하려면 두 폴더를 먼저 --rerender로 같은 검증 기준에 맞춘다
python main.py --compare-runs "results/.../실행A" "results/.../실행B"

# 실행 (기획보고서 원문 모드 — .md/.txt, HWP는 md로 변환 후 투입)
python main.py --report "내사업_기획보고서.md"

# 보고서 위치가 바뀌어도 같은 사업으로 추적하려면 명시적 사업 ID 지정
python main.py --report "내사업_기획보고서.md" --report-project-id my-rnd-project

# 독립 조사자료를 함께 넣어 사업보고서 주장과 교차검증
python main.py --report "기획보고서.md" --evidence "NTIS_유사과제.md" --evidence "특허조사.txt"

# 체크포인트 활성화 후 장애 복구에 사용할 실행 ID 지정
# .env: RDAGENTS_CHECKPOINT_ENABLED=true
python main.py --project quantum_computing --execution-id review-2027-quantum-01

# 디버그 모드
python main.py --project bio_health --debug
```

## 산출물

실행이 끝나면 프로젝트 내부 `results/{사업ID}/{실행ID}/`에 심의 전 과정이 저장됩니다.
`RDAGENTS_RESULTS_DIR` 환경변수를 지정하면 외부 저장소로 변경할 수 있습니다.

| 파일 | 내용 |
|---|---|
| `00_입력문서_출처.md` | 입력 파일, 청크 수, 출처 표기 규칙 |
| `00b_사전점검.md` | 맨 앞에 **사업 유형 판별** 결과와 근거 줄. (원문 모드) 심의 전 규칙 기반 점검: 필수 9개 항목(공공임무형·혼합형은 재난안전 항목 4개 추가, 13개)의 충족·근거 약함·누락과 근거 줄. 주 보고서만 보므로 `--evidence` 근거 파일에만 있는 내용(예: 유사·중복 검토 파일)은 누락으로 나올 수 있음. 누락·약함 항목은 심사위원 패널과 예상 질의 추출기에 우선 확인 지점으로 전달. **숫자 검산**: 표의 열·행 합계, 단가×수량, 비율, 본문의 총액 내역 합계·증감률, 본문 금액↔표 합계를 코드로 다시 계산해 불일치(최대 3건, 틀린 칸 추정 우선)도 함께 전달하고, 불일치가 있으면 예상 질의 추출기가 이를 다루는 질의·보완 권고를 1건 이상씩 반드시 넣음 (LLM 호출 없음) |
| `01_분석_분야기술전문가.md` | 분야 기술전문가 3명의 검토 (전문가별 절) |

| `02_심사공방_전문.md` | 쟁점별 공방 전문: [심사위원 패널 · 위원] (쟁점 #) 질의 → [사업 발표자] 답변 → 코드 판정 |
| `02b_쟁점원장.md` | 쟁점별 심의기준·심각도·출처(원문 대조 결과)·질의 위원·방어 결과와 판정 근거. HTML 의결 요약과 실행 비교에도 집계 |
| `03_전문위원회_의견.md` | 위원장 1차 심의 의견 |
| `04_예산조정안.md` | 예산 조정관 1차 조정안 |

LLM이 쓴 산출물에서 단위 붙은 수치(%, 억 원, 명 등)가 입력 원문 어디에도 없으면 해당 줄 끝에 `⚠️[원문에 없는 수치: …]`를 붙임. 이 표시는 심의 도중에도 붙음: 분석 보고서와 공방·재정 토론 기록은 노드가 쓴 직후 표시되고, 근거 사용 원칙이 뒤 노드에게 표시된 수치를 사실로 옮겨 쓰지 말라고 지시함 (위원장 의견·예산 조정안·최종 결정 같은 JSON 필드는 글 값에만 표시). 단위가 열 제목('피해액 비율', '금액(억 원)')이나 `(단위: …, %)`에만 있는 표 숫자와 사전 점검이 계산한 값은 원문 수치로 봄. 다시 렌더링하면 지난 표시를 지우고 지금 규칙으로 다시 붙임. 앞쪽 **검증 안 된 수치 요약** 표는 같은 수치를 한 행으로 묶어 나온 줄 수·문서·처음 나온 문장을 보여줌 (많이 번진 수치부터). '2개월' 같은 기간은 개수로 보지 않음. 원문의 천원·백만원 금액(표의 '(백만원)' 열 포함)과 억·조 금액은 서로 바꾼 값도 원문 수치로 봄(14,160백만원 = 141.6억 원). 다만 1억·1조 미만 값은 그 단위로 바꾸지 않음 (반올림 허용 범위로 지어낸 값이 통과하지 않게) |
| `12_실행관측성.md` | 실행 ID·모델·노드 시간·토큰·비용 계산 상태 |
| `심의종합리포트.html` | 위 산출물을 목차와 섹션으로 묶은 단일 열람용 HTML 리포트. 원문에 없는 수치가 있으면 심의 의결 바로 아래에 '검증 안 된 수치' 표를 실음 |

같은 사업을 보완 후 다시 심의하면 이전 심의 요약(`~/.rdagents/memory/review_memory.md`)이
자동으로 주입되어, 위원장과 최종 승인권자가 지적사항 해소 여부를 확인합니다.
원문 보고서는 기본적으로 절대 파일 경로 기반의 안정 ID를 사용하므로 같은 경로에서 수정한 보완본은
같은 사업으로 인식하고, 다른 경로의 동명 보고서는 구분합니다. 파일을 이동하면서도 이력을 이어가려면
`--report-project-id`를 명시하세요. 과거 이력은 기본적으로 최근 5건, 최대 12,000자만 주입됩니다.

원문 모드에서는 보고서 전문을 매번 전달하지 않고, 줄 번호를 보존한 로컬 청크 인덱스에서 분석 관점과
관련된 부분만 검색합니다. 분석가는 `search_report` 도구로 원하는 주제어를 직접 검색해 근거 구절을
추가 확보할 수 있습니다. 검색 결과는 `[출처: 파일명 L시작-L끝]` 형식으로 표시됩니다. 원문은 신뢰할 수
없는 분석 데이터로 구획되어 문서 안의 역할 변경·명령·출력 지시를 따르지 않도록 처리합니다.
`--evidence`로 독립 조사자료를 여러 개 추가하면 검색 결과에 사업보고서와 외부근거를 구분하여 함께
제공합니다. 외부 자료는 자동으로 신뢰되는 사실이 아니라 교차검증 대상이며 동일한 신뢰 경계를 적용합니다.

`RDAGENTS_CHECKPOINT_ENABLED=true`이면 SQLite 체크포인트가
`~/.rdagents/checkpoints/reviews.sqlite`에 저장됩니다. 장애 후 같은 `--execution-id`를 사용하면 동일
LangGraph 실행 이력을 기준으로 재개할 수 있습니다. LLM 공급자의 **하루 사용량 한도**(예: Groq TPD)에
걸리면 몇 초 간격 재시도를 하지 않고 즉시 멈춘 뒤(종료 코드 3) 대기 시간과 이어서 실행할 명령을 안내합니다.
분당 한도는 기존처럼 잠시 기다렸다 재시도합니다. 실행 관측성에는 공급자가 응답에 제공한 토큰 메타데이터만
기록하며, 가격은 시점·계약별 차이가 있어 별도 가격표가 없으면 비용을 임의 계산하지 않습니다.

응답이 출력 토큰 한도에서 끊기면(`finish_reason=length`) 경고를 남기고, 글 응답 끝에 "[출력 토큰 한도에 걸려 여기서
잘렸습니다]"를 붙여 뒤 단계와 사람이 잘린 것을 알게 합니다 (gpt-oss는 추론 토큰도 출력 한도를 씀).

구조화 출력(심의 의견·예산안·최종 결정·예상 질의 등)이 스키마 검증에 실패하면 오류 내용을 피드백하여
자동 재시도하고, 그래도 실패하면 자유 텍스트 폴백으로 이어집니다. 폴백으로 끝난 결정은 재심의
이력(memory)에 기록하지 않습니다. 예상 질의는 최소 5건, 보완 권고는 최소 3건이며 3대 심의기준
(정부지원 필요성·기술개발의 중요성·시급성)과 **예산 타당성**(예산 규모·비목 산출 근거)을 겨냥한 질의가
각각 1건 이상 포함되도록 검증합니다. 예산 질의를 따로 요구하는 이유는 3대 기준만으로는 감액 결론을 좌우하는
예산 근거 질의가 빠져도 통과하기 때문입니다. 심사위원 패널도 공방 전체에서 예산 산출 근거를 최소 1회 묻습니다.

검증보고서는 출처 형식·줄 범위 검사에 더해 **출처 내용 대조**를 합니다. 출처가 달린 문장의 단위 붙은 수치
(억 원·%·명 등)가 인용 줄에 없거나, 문장과 인용 줄이 공유하는 단어가 없으면 "확인 권고"로 표시합니다.
gpt-oss가 쓰는 비슷한 하이픈(`L3‑L4`)은 `-`로 맞추고, `(NDMI-기본-2025-20)…`처럼 줄여 쓴 파일명은 앞부분이 입력 파일 하나와만 맞을 때 그 파일로 봅니다 (NDMI 실행: 잘린 출처 35건 → 0건). 줄임표 뒤에 공백 없이 붙은 줄번호(`…L3-L7`), 앞 괄호가 빠진 이름(`NDMI-기본-2025-20…`), 가운데를 줄인 이름(`(NDMI-기본-2025-20)…md`, 끝부분도 맞아야 함), 한 인용에 나열한 범위 여러 개(`L319-L319, L314-L314`)도 해석합니다 (groq4 실행: 이슈 12건 → 0건). 법조문("제2조"), 표의 숫자만 있는 칸, 코드가 만든 사전 점검 파일은 내용 대조에서 빼고, 한 줄에 출처가 여럿이면 인용 줄을 합쳐 대조합니다.
줄 범위는 맞지만 엉뚱한 줄을 인용한 경우를 잡기 위한 경험적 검사라 검증 상태(통과/검토 필요)에는 반영하지
않고 원문 대조 대상만 알려 줍니다.

## 실전 대비 워크플로우 (원천 목표: 예산 확보)

시뮬레이터의 성공 기준은 "실제 심의 질의를 미리 맞히는 것"이며, 아래 루프로 적중률을 측정·개선합니다.

```bash
# 1) 관문을 지정해 모의 심의 실행 (부처심의 / 예타 / 예산조정 / 국회)
python main.py --report "기획보고서.md" --gate 예타
#    사업 유형 판별이 틀리면 직접 지정: --project-type 공공임무형

# 2) 예상 질의로 답변 리허설 (대화형 모의 청문 — 답변 평가 + 압박 후속질의)
python main.py --hearing --run-dir "results/{사업ID}/{실행ID}"

# 3) 실제 심의 후: 실제로 받은 질의를 파일로 정리해 적중률 검증
python main.py --verify-questions "실제질의.md" --run-dir "results/{사업ID}/{실행ID}"
```

모의 심의의 공방은 실제 심의장 구조를 따릅니다 — 옹호 위원 없이 **심사위원 패널이 공격하고
사업 발표자가 방어**하며, 방어에 실패한 지점이 예상 질의와 보완 권고로 이어집니다.

예상 질의는 `question_bank_seed/`의 전형 질의 패턴을 참고해 생성되고, `--verify-questions`를
거친 실제 질의는 `~/.rdagents/question_bank/`에 자동 축적되어 회차가 쌓일수록 예측이 실전에
가까워집니다. 적중률 이력은 `~/.rdagents/verification/history.jsonl`에서 추세를 확인할 수 있습니다.
